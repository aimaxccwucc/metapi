# 接入与诊断工作台升级

本文档基于对参考项目 [Yoan98/ai-key-manage](https://github.com/Yoan98/ai-key-manage) 的对照审阅，整理哪些能力适合 Metapi 借鉴、哪些不应直接照搬，以及如何在不偏离 Metapi 当前定位的前提下，补齐“接入效率 + 单凭证诊断 + 默认模型推荐”这条产品链路。

[返回文档中心](./README.md)

---

## 结论

`ai-key-manage` 值得借鉴的重点，不是它的技术栈或轻量页面本身，而是它把一条高频链路收得很短：

- 粘贴一段现成配置
- 快速判断 Key / 地址是否可用
- 读取可见模型
- 跑几轮测速
- 给出一个更适合作为默认模型的建议

Metapi 当前已经具备更强的后端底座，包括：

- 多站点、多账号、多 Token、多路由治理
- 协议探测与协议兼容转换
- 模型广场、模型测试器、导入导出、下游 Key 管理
- 后台任务、健康检查、程序日志、路由决策与失败治理

真正的缺口不在“能力有没有”，而在“单条接入链路是否够短、够顺、够可解释”。

因此，本轮升级建议聚焦为一句话：

把现有分散在 `站点管理`、`账号管理`、`模型测试器`、`模型广场`、`导入导出` 里的能力，收敛成一个更顺手的 `接入与诊断工作台`。

## 参考项目可确认的特点

从参考仓库可直接确认，它主要解决的是“个人长期维护多套 OpenAI 兼容 Key”的轻量场景，核心特点包括：

- 支持粘贴解析 `curl`、JSON、环境变量风格文本、结构化文本和 `ccswitch://` 链接。
- 支持对单条配置做连通性测试。
- 支持读取 `/models`，必要时对少量候选模型做有限试探。
- 支持按模型做 1 到 3 轮测速，并汇总平均耗时、中位耗时、首字时间、成功率、稳定性。
- 支持给当前配置推荐一个默认模型。
- 默认把配置保存在浏览器 `localStorage`，真实请求通过同源后端转发。

这套设计非常适合“单用户、本地优先、无数据库”的 Key 工作台。

## Metapi 当前已经具备的基础

对照当前仓库，可以确认 Metapi 已经具备以下可复用基础，不需要重新造一套：

- 已有站点接入、站点探测和协议探测链路。
- 已有账号校验、模型读取、Token 同步、健康刷新与修复能力。
- 已有 `模型测试器`，支持多协议、多模式和本地会话持久化。
- 已有 `模型广场`、站点测速、路由决策与治理态展示。
- 已有实例级导入导出和 WebDAV 备份同步。
- 已有下游 Key 管理，适合承接“面向客户端分发”的能力。

换句话说，Metapi 的问题不是后端能力不足，而是缺一个更聚焦的“前台工作流”。

## 最值得借鉴的点

### 1. 粘贴即解析的接入入口

这是参考项目最值得借鉴的点，也是 Metapi 当前最缺的入口体验。

当前 Metapi 的接入路径偏管理后台思维：先建站点，再建账号，再看 Token，再去模型测试或模型广场排查。这个流程适合长期运维，但不适合“我手里刚拿到一段 `curl` / 一组 `BASE_URL + API_KEY + MODEL`，想马上试通”的场景。

建议补一个 `快速接入` 入口，支持：

- 粘贴 `curl` 命令，解析出 `baseUrl`、`Authorization`、模型名、额外头。
- 粘贴 JSON 请求体或环境变量文本，解析出常见字段。
- 允许一次粘贴多组配置，先预览，再选择导入哪些条目。
- 解析结果先进入草稿区，不直接写库；只有用户确认后才落到站点 / 账号 / Token。

这项能力优先放在前端实现，草稿态默认存在浏览器本地，不直接污染数据库。

### 2. 单凭证诊断闭环

参考项目把“能不能用、有哪些模型、哪个更适合默认”串成了一条很短的操作链。Metapi 当前这些能力分散在不同页面里，导致排查一个新上游或新账号时跳转较多。

建议新增一个 `接入诊断工作台`，围绕“单个站点 / 单个账号 / 单个 Token”提供统一视图：

- 连通性结果：地址是否合法、接口是否可达、鉴权是否通过。
- 协议结果：当前更像 OpenAI / Claude / Gemini 哪条入口。
- 模型结果：优先显示上游返回的模型列表；若是显式手动诊断场景，可做有限候选试探。
- 调试结果：直接联动现有 `模型测试器` 或 `测试代理` 接口，展示原始请求与关键错误信息。
- 路由结果：如果该凭证已经被挂到路由上，同时展示最近路由决策与治理状态。

这会比单独强化某个页面更划算，因为它复用的是现有后端能力，只是把入口重新编排。

建议把这节再明确为一套可实施的设计，而不是只停在页面概念。

#### 目标

- 让运维者拿到一条新上游或新账号后，可以在一个页面内完成首轮排查。
- 把“连不通”“协议不匹配”“模型不可见”“路由被治理隔离”这些常见问题，收敛成可解释的结构化结果。
- 让诊断结论能自然衔接到现有正式页面，而不是做成孤立的一次性工具。

#### 适用对象

- 新接入一个站点，想快速确认它更适合 OpenAI / Claude / Gemini 哪种协议路径。
- 某个账号、Token 或上游突然不可用，需要定位问题是在网络、认证、协议还是模型层。
- 某条凭证已经挂到路由或下游 Key 上，需要确认问题是在源头还是在治理状态。

#### 非目标

- 不做新的统一代理执行引擎。
- 不把工作台变成新的常驻运维首页，仍然是“单对象首轮诊断入口”。
- 不在这个页面里直接承担批量站点治理、全局观测或路由治理总览。

#### 建议交互结构

建议页面采用三栏或三段式结构：

- `诊断对象区`
  - 选择来源：站点、账号、Token、临时草稿。
  - 显示对象基础信息：站点名、URL、账号名、最近更新时间、是否已挂路由。
  - 若来自草稿，则明确标注“未入库，仅当前浏览器会话可见”。
- `诊断结果区`
  - 连通性卡片：地址归一化结果、接口是否可达、耗时、HTTP 状态。
  - 协议卡片：优先显示站点协议探测结果，标明探测来源是缓存还是实时结果。
  - 模型卡片：显示模型列表来源、可见模型数量、是否触发过有限候选试探。
  - 调试卡片：展示一次最小测试请求的摘要结果，可一键跳转到模型测试器打开完整调试。
- `关联影响区`
  - 当前是否被路由引用。
  - 最近一次路由决策快照是否命中过该对象。
  - 是否存在 `suppressed / probing` 等治理状态。
  - 若已有下游 Key 绑定相关路由，也在这里提示影响范围。

#### 建议执行顺序

建议把诊断流程固定为 5 步，避免页面行为随实现细节漂移：

1. 归一化输入
2. 连通性检测
3. 协议探测
4. 模型读取
5. 最小测试请求

顺序原因：

- 先做 URL 和鉴权归一化，能尽早过滤掉明显错误。
- 协议探测应早于测试请求，避免拿错协议去打上游，制造混淆错误。
- 模型读取优先于调试请求，能让后续测试默认使用上游实际可见模型，而不是拍脑袋猜模型名。

#### 复用现有能力

这一页应尽量复用现有接口，而不是再加一套平行后端：

- 站点协议：复用 `POST /api/sites/:id/protocol-probe`
- 账号模型读取：复用现有账号模型获取与刷新链路
- 最小请求调试：复用 `src/server/routes/api/test.ts` 暴露的测试代理能力
- 路由治理态：复用路由治理概览、治理对象列表、路由诊断与决策快照接口
- 深度调试：复用现有 `模型测试器` 页面作为“进入高级调试”的下钻目标

如果诊断对象是“临时草稿”而非正式账号，则只补最小必要的新编排接口，不复制现有执行逻辑。

#### 建议结果模型

建议工作台的结果区统一输出一份结构化摘要，至少包含：

- `connectivity`
  - `normalizedUrl`
  - `reachable`
  - `statusCode`
  - `latencyMs`
  - `message`
- `protocol`
  - `resolvedProtocol`
  - `probeSource`
  - `endpoint`
  - `confidence`
  - `detail`
- `models`
  - `source`
  - `visibleCount`
  - `recommendedBaseModel`
  - `truncated`
  - `detail`
- `debug`
  - `requestPath`
  - `requestFormat`
  - `ok`
  - `errorSummary`
  - `rawPreview`
- `routing`
  - `referencedByRoutes`
  - `governanceState`
  - `governanceReason`
  - `recentDecisionSummary`

这样后续无论是页面展示、事件记录还是导出诊断结果，都不需要从多个接口结果里临时拼装文案。

#### 失败分类建议

页面不应只返回“失败”，而应按当前仓库已有治理与探测语义归类：

- 网络或地址问题
- 认证失败
- 协议不匹配
- 模型不存在或模型不可见
- 上游限流或余额问题
- 路由治理隔离
- 未知但可复现

这些分类要尽量复用现有 `probeClassification`、治理原因码和测试代理错误，不要再造一套命名体系。

#### 与现有页面的关系

工作台不是替代这些页面，而是作为首轮入口：

- 需要改正式信息时，跳转到 `站点管理`、`账号管理`、`Token 管理`
- 需要做多轮复杂调试时，跳转到 `模型测试器`
- 需要看治理全貌时，跳转到 `路由管理` 或治理相关页面
- 需要看请求证据时，跳转到 `代理日志` 或 `程序日志`

#### 最小实施版本

这一节建议按最小版本落地：

1. 仅支持从现有站点/账号进入诊断
2. 先聚合现有接口结果，不新增草稿态临时账号诊断
3. 页面只读，不直接写站点或账号
4. 先做“查看结果 + 跳转修复”，后续再加“在工作台内直接修复”

这样实现成本最低，也最不容易引入新的状态同步问题。

### 3. 模型测速与默认模型推荐

Metapi 目前已经有站点级测速和通用模型测试能力，但缺少一个面向“单条凭证配置”的轻量测速闭环。

建议借鉴参考项目的几个具体做法：

- 对同一模型支持 1 到 3 轮轻量测速。
- 指标统一展示：平均耗时、中位耗时、首字时间、成功率。
- 默认跳过明显不适合对话测速的模型，例如 embedding、rerank、部分图片类模型。
- 在测速结束后给出一个“推荐默认模型”，但要明确推荐依据。

Metapi 的优势是，这个推荐不必只停在单个模型名上，还可以继续往下游联动：

- 可选择回填到账号默认模型。
- 可选择作为某条路由的默认候选模型之一。
- 可选择生成新的下游 Key 使用建议。

建议把这一节进一步明确成“手动诊断场景下的轻量评测”，而不是新的后台探测任务。

#### 目标

- 在单凭证诊断完成后，帮助运维者快速挑出一个更适合作为默认模型的候选。
- 用尽量低的请求成本，给出足够稳定的判断依据。
- 输出结果既可被人直接采用，也可成为后续回填正式配置的建议输入。

#### 非目标

- 不做全站、全账号、全模型的定时测速。
- 不做高成本压测，不追求严格性能基准。
- 不把测速结果直接写成路由治理事实或能力事实。

#### 触发条件

测速只在显式手动场景触发：

- 用户在诊断工作台中点击“开始测速”
- 用户已经选定单个站点 / 账号 / Token
- 用户已经拿到一组待测模型列表

默认不在这些场景自动触发：

- 新站点创建成功后
- 协议探测结束后
- 路由治理恢复时
- 模型广场后台刷新时

#### 候选模型来源

模型候选建议按优先级来源收敛：

1. 上游显式返回的模型列表
2. 当前账号已有手工模型列表
3. 用户手动勾选补充模型
4. 显式手动触发时的有限候选试探结果

这里要继续遵守现有稳定性约束：

- 有限候选试探只能作为人工诊断兜底
- 不能把试探结果写成“站点全模型全集”
- 不能用于后台批量扫描

#### 默认过滤规则

测速前建议先做一层默认过滤，减少无效开销：

- 排除 embedding、rerank、moderation、speech、image、video 等明显非对话模型
- 排除名称中已知不支持普通 chat 请求的模型
- 允许用户手动取消过滤并强制加入某个模型

过滤逻辑应当是“默认建议”，不是硬禁止。

#### 评测方式

每轮评测只做最小充分请求：

- 请求体尽量短
- `max_tokens` 取小值
- 首选流式请求，用于获取 `firstTokenMs`
- 流式不可用时退回非流式请求

建议固定两档：

- `1 轮快速评测`
  - 用于首轮筛选
  - 低成本、低等待
- `3 轮标准评测`
  - 用于在几个候选之间做更稳妥判断

不建议继续增加更多轮次作为默认 UI 入口，否则会明显拉高成本和等待时长。

#### 指标定义

建议统一展示以下指标，并明确其用途：

- `avgLatencyMs`
  - 总体平均耗时
  - 用来衡量“总体速度”
- `medianLatencyMs`
  - 中位耗时
  - 用来压制极端值影响
- `firstTokenMs`
  - 首字时间
  - 更接近日常对话体感
- `successRate`
  - 成功轮次 / 总轮次
  - 用来衡量稳定性
- `sampleCount`
  - 本次实际返回结果的轮次
  - 防止把 1 次成功误读成稳定

#### 推荐默认模型规则

推荐不应只给一个名字，还要给出推荐理由。建议规则如下：

- 若成功率明显低于其他候选，不进入推荐
- 在成功率接近的前提下，优先比较中位耗时
- 若中位耗时接近，再比较首字时间
- 若首字时间接近，再比较平均耗时

建议把推荐理由显示成结构化文案，例如：

- `推荐：gpt-4.1-mini，3/3 成功，中位耗时最低，首字时间稳定`
- `推荐：claude-3-5-sonnet，首字最快，但平均耗时略高`

这样运维者能理解系统为什么推荐，而不是只看到一个黑盒结论。

#### 结果落点

测速结果建议分为三层落点：

- 当前会话结果
  - 默认放浏览器本地，仅用于当前诊断页展示
- 建议动作
  - “设为账号默认模型”
  - “加入某条路由候选”
  - “为下游 Key 生成推荐模型片段”
- 正式配置写入
  - 只有用户点击确认后才进入正式配置

这能避免“刚测完一次就把正式路由改掉”的风险。

#### 与现有页面协同

测速能力建议放在 `接入诊断工作台` 中作为轻量模式存在，但不要替代现有页面：

- 复杂多协议、多模态、多文件调试仍然去 `模型测试器`
- 宏观可见性与大盘仍在 `模型广场` 和仪表盘
- 路由级问题仍回到路由页和治理页

#### 实施顺序

建议按下面顺序做：

1. 先复用现有测试代理链路实现单模型 1 轮/3 轮评测
2. 再做指标汇总和推荐文案
3. 最后再加“回填账号默认模型 / 生成下游 Key 建议”按钮

这样可以把“评测能力”和“写正式配置”的风险拆开。

### 4. 面向客户端的定向导出

参考项目做了导出和 CC Switch 联动，本质上解决的是“把一条配置快速交给另一个客户端继续用”。

Metapi 不适合直接照搬“导出上游 Key 到各种 App”的思路，但可以把它转换为更安全、更符合网关定位的能力：

- 为下游 Key 生成客户端接入片段，例如 `curl`、OpenAI SDK、Cherry Studio、Open WebUI 等。
- 默认导出的是 Metapi 网关地址 + 下游 Key，而不是上游原始凭证。
- 允许把“推荐模型、允许模型范围、对应路由”一起打包到说明片段里。

这样保留了参考项目的“分发效率”，但不破坏 Metapi 的权限边界。

这一节建议进一步明确为“受控分发助手”，不是“把配置随便导出”。

#### 目标

- 让运维者能把一个已经诊断过、策略已明确的访问入口，快速交付给客户端使用。
- 导出的内容默认是受控、可撤销、可限权的下游接入信息。
- 把现有 `下游 Key 管理` 从“只看策略字段”增强成“能直接给客户端接入说明”的交付页。

#### 非目标

- 不默认导出上游站点地址和原始 Key。
- 不做任意 App 的深度专有协议适配作为首要目标。
- 不绕开下游 Key 的权限模型，直接分发全局 `PROXY_TOKEN`。

#### 建议归属页面

这项能力更适合落在现有 `下游 Key 管理` 页，而不是放在导入导出页：

- `导入/导出` 页服务的是实例迁移和备份
- “定向导出给客户端”服务的是下游凭证分发

两者语义不同，放一起容易混淆“备份”和“分发”。

#### 导出前置条件

只有满足以下条件时，才建议展示“生成接入片段”：

- 已存在正式下游 Key
- 下游 Key 已配置或可推导允许模型范围
- 若绑定路由，则路由本身处于启用状态
- 若当前来自诊断工作台，至少已有一个建议默认模型或手动指定模型

如果这些条件不满足，应提示先去完善策略，而不是输出一个不完整片段。

#### 默认导出内容

建议默认生成以下内容，而不是原始 JSON 备份：

- 网关基地址
- 下游 Key
- 推荐默认模型
- 允许模型范围摘要
- 受限路由摘要
- 客户端示例代码或配置片段

可选附带：

- 说明该 Key 的用途，例如“移动端灰度”“评测专用”“只允许 GPT 系列”
- 过期时间和使用限制提醒

#### 支持的导出形式

建议第一阶段只做文本型导出：

- `curl` 示例
- OpenAI SDK 示例
- 通用环境变量片段
- 常见客户端说明片段，例如 Open WebUI、Cherry Studio

这样实施成本低，也更容易审查安全边界。

像 `ccswitch://` 这类深链适配可以放到后续阶段，不应作为首发范围。

#### 与下游 Key 策略的联动

Metapi 当前的下游 Key 已有一套很适合做导出约束的策略字段，包括：

- `supportedModels`
- `allowedRouteIds`
- `siteWeightMultipliers`
- 启停状态、分组和标签

导出助手应基于这些正式策略生成说明，而不是额外维护一套“导出时专用配置”。

例如：

- 若配置了 `supportedModels`，导出片段里直接把推荐模型限制在这组范围内
- 若配置了 `allowedRouteIds`，导出文案里标明此 Key 仅命中特定路由
- 若 Key 已禁用或即将过期，则导出按钮置灰或附带警示

#### 安全边界

这节必须写清楚几个不能退让的边界：

- 不导出上游原始密钥
- 不导出管理后台登录态
- 不导出全局 `PROXY_TOKEN`
- 不把工作台草稿里的临时凭证直接包装成可长期传播的客户端配置

必要时可提供“复制时二次确认”，明确提示用户当前复制的是“下游受控访问凭证”。

#### 与诊断工作台的协同

这项能力和前两节的关系应当是：

1. 先在诊断工作台确认该对象可用
2. 再拿到测速与默认模型建议
3. 最后在下游 Key 管理里生成定向接入片段

也就是说，诊断工作台可以提供“去生成导出片段”的跳转入口，但不建议在工作台里直接承担完整导出页面职责。

#### 分阶段实施建议

建议按三个阶段落地：

1. `P0`
   - 为现有下游 Key 生成 `curl`、环境变量和 OpenAI SDK 示例
2. `P1`
   - 把推荐模型、模型限制、路由限制写进说明模板
3. `P2`
   - 再考虑特定客户端模板或深链导出

这样既能快速产生可见价值，又不会在首轮把适配面铺得过大。

### 5. 草稿态与正式数据分层

参考项目把未保存配置先放在本地草稿里，这一点很适合 Metapi 借鉴。

建议把以下数据明确分层：

- 草稿态：粘贴解析结果、未确认导入项、临时测速结果、最近一次诊断会话。默认保存在浏览器本地。
- 正式态：已创建的站点、账号、Token、路由、下游 Key。保存在服务端数据库。

这样既能提高首次接入效率，又不会让“试一下”的数据把管理库污染得很乱。

## 不建议直接照搬的点

### 1. 不要把 `localStorage` 当正式数据源

参考项目是单用户轻工具，`localStorage` 作为主存储成立。Metapi 是长期运行的网关与管理后台，站点、账号、路由和下游 Key 必须继续以服务端数据库为准。

因此，`localStorage` 只适合存放：

- 粘贴解析草稿
- 工作台筛选条件
- 最近一次未保存的测试会话

不适合承载：

- 正式凭证数据
- 团队共享配置
- 治理状态或历史诊断基线

### 2. 不要把轻量同源代理思路扩成第二套网关

参考项目的后端代理主要是为了解决浏览器直连上游的 CORS 问题。Metapi 已经有完整代理网关、协议转换和测试接口，不应该再为“工作台功能”新增一套平行请求链。

正确做法是复用现有：

- `/api/test` 相关接口
- 账号验证与模型读取接口
- 站点协议探测接口
- 现有代理入口与模型测试器能力

### 3. 不要把候选模型暴力试探扩成全站自动枚举

这一点要特别注意。

Metapi 当前稳定性文档已经明确约束：协议探测只能做“单模型有限验证”，不允许自动枚举一个站点的全部模型。参考项目中的候选模型试探，只适合作为“用户主动发起的单凭证诊断”里的有限兜底，不适合迁移成：

- 后台定时全站扫描
- 新站点创建后的自动全量试探
- 路由治理过程中的批量模型探测

如果要借鉴，只能放在显式手动场景里，并加上边界：

- 仅针对当前正在诊断的一条凭证
- 限定候选模型数量
- 有超时、失败分类和冷却
- 结果不自动当成全站真实能力全集

### 4. 不要默认导出上游真实凭证

参考项目的使用场景是“自己管理自己的 Key”。Metapi 的定位是网关和运维中台，默认应优先输出下游受控凭证，而不是把上游真实 Key 到处分发。

## 面向 Metapi 的落地方案

### 阶段 1：补一个 `快速接入` 入口

目标：把“拿到一段配置，5 分钟内接通并看到模型”变成默认体验。

建议实现：

- 新增独立页面或侧边抽屉：`快速接入`。
- 支持粘贴 `curl` / JSON / 环境变量文本。
- 解析后生成草稿卡片：站点地址、鉴权方式、模型、附加头、来源类型。
- 卡片支持三步联动：`识别站点`、`验证凭证`、`导入为正式连接`。

优先复用现有接口，不先新增重后端。

### 阶段 2：做 `接入诊断工作台`

目标：把站点、账号、Token、模型测试、错误分类统一到同一页。

建议视图结构：

- 左侧：当前诊断对象与基础配置。
- 中间：协议探测、鉴权结果、模型列表、轻量测速。
- 右侧：原始错误、最近一次测试结果、最近路由决策、治理状态。

这样可以把当前分散在多个页面里的首轮排障动作收束起来。

### 阶段 3：补 `模型测速 + 推荐默认模型`

目标：把“接通了”继续推进到“知道该默认用哪个模型”。

建议规则：

- 默认只对用户选中的、或系统判定适合对话的模型测速。
- 每轮请求尽量使用最小 prompt、最小 token 上限。
- 推荐结果需要解释原因，例如：
  - 首字更快
  - 总耗时更稳
  - 成功率更高

推荐结果默认只作为建议，不自动改写路由配置。

### 阶段 4：补 `客户端导出助手`

目标：把诊断后的结果安全地下发给实际使用方。

建议导出内容：

- 网关地址
- 下游 Key
- 推荐模型
- 可选模型范围
- 对应客户端示例片段

这一阶段更适合作为 `下游 Key 管理` 页的增强，而不是新建一套独立导出系统。

## 推荐优先级

建议按以下优先级推进：

| 优先级 | 事项 | 原因 |
|------|------|------|
| P0 | 快速接入粘贴解析 | 直接缩短首次接入时间，投入小、收益高 |
| P0 | 单凭证诊断工作台 | 能把现有分散能力收拢，减少页面跳转 |
| P1 | 模型测速与推荐默认模型 | 接通后下一步最自然，用户感知强 |
| P1 | 下游 Key 导出助手 | 能把运维结果更安全地下发给客户端 |
| P2 | CC Switch 或特定 App 深链 | 有价值，但不应先于主工作流 |

## 最小可实施版本

如果只做一轮最小升级，建议先落下面这组：

1. 新增 `快速接入` 页面，支持粘贴解析。
2. 复用现有接口做 `识别站点 -> 验证凭证 -> 拉取模型` 三步诊断。
3. 在当前页补一个轻量测速区，只支持 1 轮和 3 轮两档。
4. 生成“推荐默认模型”与“导入正式连接”按钮。

做到这一步，Metapi 就已经吸收了参考项目最有价值的产品体验，同时仍保持当前网关中台的定位，不会退化成另一个本地 Key 小工具。

## 后续实施建议

如果进入实现阶段，建议按这个顺序拆任务：

1. 前端先做粘贴解析器和草稿态管理。
2. 再拼接现有后端接口，形成完整诊断页。
3. 再补测速汇总与推荐逻辑。
4. 最后再做下游 Key 导出模板和客户端联动。

原因很简单：前两步几乎全部建立在现有能力之上，风险最低，也最容易先交付用户可感知收益。
