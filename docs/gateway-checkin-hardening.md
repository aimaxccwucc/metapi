# 路由网关与签到稳定性改造

本文档沉淀当前仓库在“路由网关稳定性”和“站点签到可靠性”上的主要问题、设计原则、外部参考与分阶段改造方案，供后续实现、评审和回归验证统一使用。

[返回文档中心](./README.md)

---

## 目标

本专项只聚焦两个方向：

- 路由调用时，优先命中稳定可用的渠道，而不是反复撞已知失败渠道。
- 站点签到时，能够清晰区分成功、需人工处理、可重试失败、永久不支持，并让调度行为和这些状态一致。

最终目标不是“增加更多猜测和兜底”，而是把当前行为收敛成一套可解释、可验证、可恢复的稳定性体系。

另外，模型广场已经承担了“模型可用性检测、账号明细排查、自动补 Key 反馈”的运维入口角色，因此与这些稳定性路径直接相关的前端交互回归，也纳入本专项统一记录。

## 约束

- 不允许自动探测一个站点的全部模型。
- 协议探测只能使用有限验证。
- 探测优先使用用户指定模型、站点首选模型、上次成功模型或单个保守测试模型。
- 不把 `manual verification / turnstile required` 这类状态记为真正成功。
- 不把单次错误文本直接放大成长期全局惩罚，除非有明确分类和恢复路径。

## 当前主要问题

## 网关与协议

### 1. 端点记忆粒度过粗

当前上游端点记忆主要按 `siteId + downstreamFormat + 粗粒度能力` 建立，没有区分账号、token、模型。

影响：

- 同一站点下不同账号或不同模型的协议差异会互相污染。
- 某个账号的一次失败，可能把其它本来可用的流量带偏。
- 容易出现“错误协议被重复尝试”或“正确协议被错误屏蔽”。

### 2. `responses -> chat` 回退成功默认不会形成稳定记忆

当前 `responses` 下游即使最终稳定落到 `chat` 成功，后续请求也可能继续先尝试 `responses`，形成“每次先失败一次再成功”的假稳定。

### 3. 协议探测会把未验证端点一起写进支持列表

当前协议探测一旦某个端点成功，就会把默认顺序中的其它端点也写进 `supportedEndpoints`，而不是只记录已验证成功端点。

### 4. 协议错误、模型错误、凭证错误边界不清

当前失败分类仍较依赖错误文本，部分“模型不存在”“权限不足”“资源不存在”会被误判为协议不兼容，继而触发长时间端点屏蔽。

### 5. 最近失败避让过于保守

当某一层候选全部只是“最近失败”时，当前路由会直接放弃该层甚至返回 `null`，而不是在必要时退化选择一个最可能恢复的候选。

### 6. 并发避让依赖固定租约

当前并发避让主要靠固定 8 秒租约，而实际流式请求经常远超 8 秒。

### 7. 模型不可用记忆缺少 TTL 与自动恢复

当前模型不可用会被持久化为 `available=false`，但读路径不看 `checkedAt`，也缺少自动复验和成功请求回写恢复机制。

## 签到与调度

### 1. `interval` 模式会把失败也当成已处理

当前 `interval` 调度会把本轮失败结果写入内存 `attemptState`，导致一个账号在整个间隔窗口内不再重试。

### 2. `interval` 模式没有防重入

调度器使用固定轮询，但没有“上一轮仍在执行中”的互斥保护。

### 3. 自动重登恢复链路被状态过滤切断

代码层存在自动重登逻辑，但调度层只拉取 `active` 账号，`expired` 账号进不了执行路径。

### 4. 人工验证被当成成功

`Turnstile` / `manual verification required` 会并入 `success=true`，调度统计和运行时健康会被污染。

### 5. `unsupported` 与 `manual required` 缺少持久化能力标记

这两类状态不会推进 `lastCheckinAt`，也没有独立的持久化 capability profile，只靠内存临时抑制。

### 6. 批处理缺少账号级异常隔离

单个账号的日志写入、通知发送、余额刷新失败，可能影响同站点后续账号的执行。

### 7. 关键异常被静默吞掉

部分失败路径没有明确日志，直接 fallback 或忽略。

## 模型广场与诊断交互

### 1. 模型广场不同视图存在能力不一致，部分功能表现为“丢失”

当前模型广场在卡片视图、表格视图、移动端详情之间并不完全等价：

- 有的视图能直接做可用性检测和复制诊断。
- 有的视图只展示静态账号信息，没有把同一套诊断操作带过去。
- 用户切换视图后，会误以为“模型广场功能丢失了”。

影响：

- 运维入口不稳定，排障动作依赖具体视图而不是具体模型。
- 用户很难形成稳定心智，不知道应该在哪个视图完成检测、复制、诊断。

### 2. 检测成功后缺少“复制成功 Key”的闭环动作

当前模型检测成功本身是正常的，但如果检测过程中自动补了可用 Key，模型广场里只有“已自动补 Key”或补 Key 信息提示，没有直接复制成功 Key 的闭环操作。

影响：

- 用户确认“检测成功”之后，仍要跳转到其它页面手工查找刚生成或刚恢复的 Key。
- 成功路径断裂，模型广场无法承担“检测成功后立即拿去用”的入口职责。

### 3. 异常详情会把列表布局撑坏，导致后续列位移或不可见

当前异常结果和诊断详情大量以内联内容塞回表格单元格。错误文本较长、诊断内容较多时，会把行高和列宽一起撑开，甚至让后面的余额列被挤掉或视觉上消失。

影响：

- 列表结构不稳定，关键信息无法持续对齐。
- 余额、延迟、账号等运维关键信息在异常场景下反而最难看清。
- 越是需要排障的时候，页面越容易变形。

## 设计原则

### 1. 先建模，再避错

稳定性优先靠明确的能力模型和失败分类，而不是无限堆正则和固定冷却时间。

### 2. 先有限验证，再持久化记忆

只有验证过的协议或模型能力才允许进入长期记忆层。

### 3. 记忆必须有恢复路径

所有“失败记忆”都需要至少一种恢复机制：

- TTL 过期
- 成功回写
- 手动清除
- 定向复验

### 4. 不扫描全站全部模型

协议探测、模型验证和站点首选协议确认都必须遵守“单模型有限验证”原则。

### 5. 把签到当成状态机，不是布尔值

签到结果至少应拆成：

- `success`
- `already_checked`
- `manual_required`
- `unsupported`
- `retryable_failed`
- `terminal_failed`

### 6. 选路和重试要分层

首选候选生成、端点回退、通道切换、跨站点降级应分别建模，不能让所有失败都触发同一套全局重选。

### 7. 诊断结果不能破坏列表结构

模型广场、账号明细、路由诊断表格中的测试结果和异常详情，应优先使用稳定布局承载：

- 次级展开行
- 抽屉
- 侧边详情面板
- 固定宽度的摘要列

不应把长错误文本直接塞进核心数据列，导致余额、延迟、状态列失去可读性。

### 8. 成功路径必须闭环

只提示“成功”但不给下一步动作，不算真正完成。对模型广场至少应满足：

- 检测成功后能直接复制关键结果
- 如果自动补了 Key，能直接复制 Key 或跳转到对应记录
- 如果检测失败，能复制诊断摘要并查看完整详情

## 目标架构

## 站点能力 Profile

建议把当前站点能力拆成两层持久化：

### Site Type Profile

用于表达“这个站点是什么”：

- 平台类型
- 凭证来源
- 是否有管理接口
- 是否支持签到
- 是否常见 Turnstile / WAF
- 模型发现来源

### Protocol Capability Profile

用于表达“这个站点当前稳定支持什么协议”：

- 已验证成功端点集合
- 首选端点
- 首选探测模型
- 上次成功时间
- 上次失败分类
- profile 版本与更新时间

## 路由候选生成

建议改成三层：

1. 先生成同优先级、同模型能力、同协议兼容的首选候选集。
2. 在候选集内按健康、成本、实时负载、会话粘性排序。
3. 只有当前层耗尽时才扩展到下一层，不要每次失败都全局洗牌。

## 并发与熔断

建议把当前“固定租约 + 简单半开”升级为：

- 真实 inflight 计数
- 短租约兜底
- 半开探测次数限制
- 探测失败指数退避
- 失败统计 TTL

## 签到状态机

签到应拆成：

- 执行结果
- 账号运行时健康
- 是否需要人工处理
- 是否允许当天再次自动重试
- 是否需要进入重试队列

### 已完成能力清单（本轮增量）

- 新增后端聚合接口：`GET /api/routes/diagnostics`（支持 `limit`）。
- 新增前端“路由稳定性诊断”面板，集中展示：
  - 端点运行时记忆 / 持久画像
  - 模型熔断与站点运行时健康
  - 持久不可用模型阻断
  - 站点协议模式摘要与签到待办站点
- 高风险失败场景补齐日志闭环：当请求在选路阶段即“无可用通道”时，也会写入使用日志，避免第三方请求在日志中漏展示。

### 后续待办（未闭环）

- `site type profile` 仍为设计态：目前只有协议能力 profile 的持久化与诊断视图，尚未形成独立的站点类型画像存储层。
- 诊断面板当前以只读观测为主，后续可增加更细粒度的“定向复验入口”（仍需坚持单模型有限探测）。

### Phase 1：协议与站点能力建模

- 引入 `site type profile` 和 `protocol capability profile`
- 协议探测只写入已验证成功端点
- 保存单个探测模型来源

### Phase 2：端点记忆收敛

- 缩小运行时记忆维度
- 区分站点、账号、模型、凭证来源
- 允许 `responses -> chat` 成功回退形成稳定记忆

### Phase 3：选路与重试分层

- 首选候选生成和重试候选生成拆分
- 不再因为“全部最近失败”直接返回无候选
- 优先同协议、同能力、同优先级退化

### Phase 4：并发与熔断治理

- 真实 inflight 计数
- 流式请求保活租约
- 半开探测退避
- 失败统计 TTL

### Phase 5：模型能力记忆恢复

- 给 `available=false` 引入 TTL 和定向复验
- 成功请求可触发局部恢复
- 支持手动 prune 旧失败记录

### Phase 6：签到状态机与调度器

- 重构签到结果枚举
- 增加 `interval` 防重入
- 引入失败重试队列
- 让 `expired` 账号重新进入自动恢复路径

### Phase 7：观测与运维工具

- 新增路由稳定性诊断视图
- 暴露端点记忆、模型熔断、站点 profile、签到待办状态
- 增加针对性清理与复验入口
- 对齐模型广场不同视图的检测、诊断、复制能力，避免切视图后功能丢失
- 检测成功且自动补 Key 时，提供直接复制 Key 或跳转目标记录的闭环动作
- 把异常详情从主表格单元格中剥离，改为稳定的详情区或抽屉，保证余额列等核心列固定可见
