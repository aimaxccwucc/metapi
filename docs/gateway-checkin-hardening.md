# 路由网关与签到稳定性改造

本文档沉淀当前仓库在“路由网关稳定性”和“站点签到可靠性”上的主要问题、设计原则、外部参考与分阶段改造方案，供后续实现、评审和回归验证统一使用。

[返回文档中心](./README.md)

---

## 目标

本专项只聚焦两个方向：

- 路由调用时，优先命中稳定可用的渠道，而不是反复撞已知失败渠道。
- 站点签到时，能够清晰区分成功、需人工处理、可重试失败、永久不支持，并让调度行为和这些状态一致。

最终目标不是“增加更多猜测和兜底”，而是把当前行为收敛成一套可解释、可验证、可恢复的稳定性体系。

另外，模型广场已经承担了“模型可用性检测、账号明细排查、自动补 Key 反馈”的运维入口角色，因此与这些稳定性路径直接相关的前端交互回归，也纳入本专项统一记录。

## 约束

- 不允许自动探测一个站点的全部模型。
- 协议探测只能使用有限验证。
- 探测优先使用用户指定模型、站点首选模型、上次成功模型或单个保守测试模型。
- 不把 `manual verification / turnstile required` 这类状态记为真正成功。
- 不把单次错误文本直接放大成长期全局惩罚，除非有明确分类和恢复路径。

---

## 审查结论

基于 2026-03 当前代码与现有诊断能力，本项目在“稳定路由”和“签到可靠性”上已经具备较完整的基础设施，但还没有完全收敛成一套稳定、可恢复、可运营的体系。

当前最重要的判断有三个：

- 网关主问题不在基础选路，而在“端点失败记忆、账号级调度、协议探测落库策略”这三个闭环还不够强。
- 签到主问题不在“能不能签到”，而在“状态机、调度快照、人工待办、自动恢复”仍偏文本驱动和内存态。
- 后续改造必须坚持“有限验证、有限记忆、有限恢复”，不能用扫全站模型或无限重试来换稳定性。

换句话说，当前项目已经不是“缺功能”，而是“需要把已有能力统一建模并补齐恢复路径”。

## 当前实现现状

### 网关与协议

### 已落地能力

- 已有分层候选过滤、选路解释、同层退化和失败回写。
- 已有通道冷却、模型熔断、站点运行时健康、持久不可用模型阻断。
- 已有运行时端点记忆和持久端点画像。
- 已有 `suggested endpoint` 推断能力，可从错误文本中识别 `/v1/chat/completions`、`/v1/messages`、`/v1/responses`。
- 已有协议探测服务，且遵守“单模型有限验证”，不会扫全站全部模型。
- 已有路由诊断聚合接口和诊断面板，可查看端点记忆、模型熔断、站点健康、不可用模型、签到待办。
- 已补齐“无可用通道”场景下的使用日志写入，降低日志漏记风险。

### 当前关键缺口

### 1. 端点阻断仍是“软阻断”

当前运行时端点记忆与持久端点画像都会在“全部候选都被 block”时回退到候选全集。

影响：

- 系统在最坏情况下仍可能重新撞回刚失败的 endpoint。
- “稳定避开坏渠道”的目标会在压力场景下失效。
- 同一个坏协议可能在短时间内被重复尝试。

### 2. `suggested endpoint` 没有真正升级成首选学习信号

当前系统已经能从上游错误中识别“请改用 `/v1/messages` / `/v1/responses` / `/v1/chat/completions`”，但失败持久化阶段主要还是写 block，没有把这个强信号转成首选恢复方向。

影响：

- 明确可纠正的协议错误仍需要多次试错才能稳定收敛。
- 会出现“每次先错一次，再自动改对”的假稳定。

### 3. 协议探测结果保存得过于保守，容易把站点锁死

当前协议探测成功后，只保存成功 endpoint，这比旧版“写入多个未验证 endpoint”更安全；但当前落库方式会把站点直接固化成单 endpoint 的 manual 配置。

影响：

- 避错能力有了，但回退空间过小。
- 当请求能力变化、上游临时退化或站点后续升级协议时，系统恢复弹性不足。

### 4. 协议探测缺少冷却、缓存和运营级保护

当前探测服务遵守有限候选，但接口层没有明确的探测频率控制、最近成功结果缓存和站点级冷却。

影响：

- 用户重复点击探测时，仍会真实打上游。
- 对正式环境高价值账号存在风控和封号风险。

### 5. 失败分类与惩罚层叠仍较分散

当前至少同时存在通道冷却、模型熔断、站点运行时健康、历史健康倍率、持久不可用模型、endpoint block 等多层惩罚。

影响：

- 恢复顺序不透明。
- 容易出现“某层已经恢复，但整体仍长时间选不到”的体验。
- 排障成本偏高。

### 6. 账号级调度能力仍然偏弱

当前系统已经有站点、通道、模型、endpoint 维度的健康状态，但对“同站点下多个账号”的调度仍然缺少单独建模。

影响：

- 当正式环境账号较多、但同模型稳定账号较少时，系统容易在账号层反复试错。
- 缺少账号级并发限制、账号级速率预算、账号级粘性会话和账号级失败衰减。

### 7. 多模态与文件请求缺少能力分桶记忆

当前多模态/文件请求为了避免误学习，默认不启用 endpoint runtime memory。

影响：

- 设计上更安全，但会让高价值请求长期无法形成稳定成功记忆。
- 图片、音频、文件类请求更容易反复走试错路径。

### 签到与调度

### 已落地能力

- 已支持 `cron` 和 `interval` 两种签到模式。
- `interval` 模式已有进程内防重入。
- `active` 和 `expired` 账号都可进入可调度范围。
- `success / skipped / failed` 已区分，`unsupported / manual verification / already checked` 也有初步语义拆分。
- 自动重登已接入签到执行链路。
- 账号运行时健康已统一成 `healthy / unhealthy / degraded / unknown / disabled`。
- 批量签到已实现“站点间并发、站点内串行、单账号异常不拖死整批”。

### 当前关键缺口

### 1. 签到结果仍主要依赖文本识别

当前 `checkinService` 内部有一套基于 message 的判断，而 `failureReasonService` 又有另一套分类逻辑。

影响：

- 状态语义存在双轨。
- 同一种失败在不同入口下可能被解释成不同结果。
- 自动恢复和前端提示难以做到统一。

### 2. 自动重登仍偏文本启发式

当前是否触发自动重登，仍主要根据 `token expired`、`new-api-user`、`access token` 这类文本来判断。

影响：

- 容易误判和漏判。
- 难以区分“认证过期”“站点风控”“参数错误”“一次性网络波动”。

### 3. 缺少独立的签到快照和人工待办模型

当前签到日志存在，但“最近一次签到状态”“是否需要人工处理”“下次可重试时间”“连续失败次数”“最近自动重登结果”等信息没有形成结构化持久快照。

影响：

- 重启后调度上下文丢失。
- 人工运营无法快速区分“应该等”“应该重登”“应该手动签到”“应该直接停掉”。

### 4. `interval` 调度的 attempt 状态仍是纯内存

当前 `intervalAttemptByAccount` 是进程内 Map。

影响：

- 服务重启后 attempt 状态清空。
- 多进程/多实例场景下无法共享调度抑制信息。

### 5. `skipped / manual required / unsupported` 在部分汇总里仍混入成功语义

当前 `manual verification required` 不再记为真正签到成功，但在部分调度汇总和统计口径中，`success=true` 仍会覆盖 `skipped` 类结果。

影响：

- “今日已签到”“站点不支持签到”“需要人工验证”这三类情况会污染成功率判断。
- 运维面板和调度决策的语义不够干净。

### 6. 缺少站点级签到失败预算、退避与熔断

当前单账号失败不会拖死整批，但站点层没有独立的签到冷却、失败预算和恢复探测策略。

影响：

- 同一个站点在连续失败时仍可能被持续尝试。
- 风控、WAF、临时故障场景下缺少主动降压。

### 7. `manual_required` 与 `unsupported` 还不是明确的运营态

当前这两类状态已经能识别，但更像日志语义和运行时状态，还没有形成明确的人工待办闭环。

影响：

- 只能“看到失败”，但不能“按类型处理失败”。
- 运营动作仍依赖人工翻日志。

### 模型广场与诊断交互

### 已落地改进

- 已有后端 `GET /api/routes/diagnostics` 聚合接口。
- 已有“路由稳定性诊断”前端面板。
- 已补齐一部分第三方请求日志闭环。

### 当前关键缺口

### 1. 模型广场在不同视图中的检测、复制、诊断闭环仍不完全一致

影响：

- 用户切视图后容易误以为功能丢失。
- 运维入口不稳定，心智不一致。

### 2. 检测成功后缺少“直接复制成功 Key”的闭环动作

影响：

- 用户仍需跳转其它页面查找最新可用 Key。
- 模型广场无法承担“测完即用”的主入口职责。

### 3. 异常详情仍可能破坏表格结构

影响：

- 列宽和行高失控时，余额等核心列会被挤压。
- 越是故障场景，列表越难读。

## 设计原则

### 1. 先做资格判断，再做失败学习

协议、模型能力、函数调用、多模态能力、账号状态、站点状态，应尽可能在请求发出前完成资格判断，减少“发出去再发现不兼容”。

### 2. 先有限验证，再持久化记忆

只有验证过的协议或能力，才允许进入长期记忆层；默认推断只能影响短期排序，不能直接进入长期配置。

### 3. 失败记忆必须有恢复路径

所有失败记忆都必须至少支持以下一种恢复：

- TTL 过期
- 成功回写
- 定向复验
- 手动清理

### 4. 不扫描全站全部模型

协议探测、模型验证、站点协议确认都必须遵守“单模型有限验证”原则。

### 5. 账号级调度优先于全局重试

当同模型稳定账号很少时，系统应先在账号层做健康排序、粘性复用、并发控制和失败衰减，而不是一味放大全局重试。

### 6. 把签到当成状态机，不是布尔值

签到结果至少拆成：

- `success`
- `already_checked`
- `manual_required`
- `unsupported`
- `retryable_failed`
- `terminal_failed`

### 7. 主动探测和被动学习分工明确

- 被动学习负责根据真实流量更新失败记忆与健康状态。
- 主动探测只负责有限验证、定向恢复和人工触发复验。

### 8. 诊断与操作要分离

诊断面板先保证“看得清”，再增加“定向清理、定向复验、人工确认”等可控操作。

### 9. 成功路径必须闭环

只提示“成功”但不给下一步动作，不算真正完成。对模型广场至少应满足：

- 检测成功后能直接复制关键结果。
- 如果自动补了 Key，能直接复制 Key 或跳转对应记录。
- 如果检测失败，能复制诊断摘要并查看完整详情。

## 外部参考与借鉴边界

### 可直接借鉴的机制

### AxonHub

适合借鉴：

- 按优先级分组后再在组内做健康感知负载均衡。
- 错误感知、连接负载、时间衰减恢复。
- 失败后优先切换到同层下一个更健康通道，而不是全局洗牌。

不建议照搬：

- 不做无限粘性会话。
- 不把它的完整网关抽象和界面体系整套搬入当前项目。

参考：

- [AxonHub 仓库](https://github.com/looplj/axonhub)
- [Adaptive Load Balancing Guide](https://github.com/looplj/axonhub/blob/unstable/docs/en/guides/load-balance.md)

### sub2api

适合借鉴：

- 账号级调度。
- 粘性会话。
- 用户级和账号级并发限制。
- 限流与速率预算。

不建议照搬：

- 不引入它的订阅/拼车业务模型。
- 只借调度和并发控制思想。

参考：

- [sub2api README_CN](https://github.com/Wei-Shaw/sub2api/blob/main/README_CN.md)

### one-hub

适合借鉴：

- 路由前先做协议能力和通道能力判断。
- 对函数调用、格式兼容、代理要求等做前置约束。

不建议照搬：

- 不把自动获取供应商模型扩展成对单站点全模型扫描。

参考：

- [one-hub README](https://github.com/MartialBE/one-hub/blob/main/README.md)

### one-api / new-api

适合借鉴：

- 健康检查、失败重试次数、缓存开关、渠道测试等都做成显式配置。
- 通道运维任务独立配置，不依赖隐式魔法。

不建议照搬：

- 不把“加权随机 + 失败自动重试”当成最终稳定性方案。
- 当前项目应优先避免撞坏渠道，而不是先撞再补救。

参考：

- [one-api README](https://github.com/songquanpeng/one-api/blob/main/README.md)
- [new-api README](https://github.com/QuantumNous/new-api/blob/main/README.md)

### All API Hub

适合借鉴：

- 站点接入时的自动识别与手动补录。
- 自动签到执行记录。
- 模型检测、诊断、复制的闭环体验。

不建议照搬：

- 不把浏览器扩展的页面自动化和临时 Cloudflare 过盾窗口直接搬进服务端。

参考：

- [All API Hub README](https://github.com/qixing-jk/all-api-hub/blob/main/README.md)

### 通用工程实践

适合借鉴：

- Envoy 的 outlier detection：区分本地错误和上游业务错误，不把所有失败混进同一个桶。
- Kong 的 active + passive health checks：被动熔断负责摘除，主动探测负责恢复。
- AWS 的 exponential backoff with jitter：失败重试必须带抖动，避免同步重试洪峰。

参考：

- [Envoy Outlier Detection](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/outlier)
- [Kong Health Checks And Circuit Breakers](https://docs.konghq.com/gateway/latest/how-kong-works/health-checks/)
- [AWS Exponential Backoff And Jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/)

## 明确不做的方向

- 不做对单站点全部模型的自动探测。
- 不把 `manual verification / turnstile required` 记为真正签到成功。
- 不用“无限自动重试”替代协议识别、账号调度和熔断治理。
- 不引入 service mesh 级复杂度去解决当前单体网关问题。
- 不把浏览器扩展侧的人工交互方案直接强塞进服务端。

## 目标架构

### 站点与协议画像

### Site Type Profile

用于表达“这个站点是什么”：

- 平台类型
- 凭证来源
- 是否具备后台管理接口
- 是否支持签到
- 是否常见 Turnstile / WAF
- 模型发现来源
- 上次识别时间

### Protocol Capability Profile

用于表达“这个站点当前稳定支持什么协议”：

- 已验证成功 endpoint 集合
- 首选 endpoint
- 首选探测模型
- 验证来源
- 上次成功时间
- 上次失败分类
- 冷却截止时间
- profile 版本与更新时间

### 账号级路由快照

用于表达“这个账号当前是否适合继续承接某类流量”：

- 账号状态
- 认证状态
- 最近成功时间
- 最近失败时间
- 连续失败次数
- 成功率 EMA
- 延迟 EMA
- 账号级速率限制窗口
- 账号级并发上限
- 粘性会话信息

### 端点学习层

建议拆成三层：

1. 运行时短期记忆：用于快速避开刚失败 endpoint。
2. 持久画像：用于服务重启后的保守恢复。
3. 定向复验：用于低频探测和人工触发恢复。

其中要特别补齐：

- `suggested endpoint -> preferred endpoint` 的学习通道。
- “全部候选都失败”时的强阻断和低频半开恢复。
- 多模态/文件请求的能力分桶记忆。

### 签到状态机与快照

签到建议拆成两个层次：

### 执行结果状态机

- `success`
- `already_checked`
- `manual_required`
- `unsupported`
- `retryable_failed`
- `terminal_failed`

### 运营快照

- 最近一次签到状态
- 最近一次签到时间
- 下次允许自动重试时间
- 是否需要人工处理
- 最近一次自动重登结果
- 连续失败次数
- 失败原因码
- 失败类别

## 分阶段改造方案

### Phase 1：统一失败语义与画像基础

目标：

- 统一网关失败分类与签到失败分类。
- 为后续熔断、恢复、诊断提供单一真源。

改造内容：

- 建立统一 failure code / category 枚举。
- 将协议错误、模型错误、认证错误、网络错误、站点错误拆开。
- 增加 `site type profile` 持久化层。
- 补齐签到快照表或等价存储结构。

完成定义：

- 路由、探测、签到、诊断都使用同一套失败语义。
- 新增/更新任何失败类型，都只需维护一处分类入口。

### Phase 2：端点学习从“软阻断”升级为“强阻断 + 半开恢复”

目标：

- 避免重复撞坏 endpoint。
- 用更少试错次数收敛到正确协议。

改造内容：

- 当全部候选都 block 时，不直接恢复全集。
- 优先 `suggested endpoint`，其次选择最久未失败 endpoint，最后才允许低频半开探测。
- 将 `suggested endpoint` 升级成 preferred 学习信号。
- 为 block 设置更明确的 TTL、恢复探测频率和人工清理入口。

完成定义：

- 同一协议错误不会在短时间内被重复撞击。
- 明确提示“请改用某 endpoint”的站点，能在下一次请求中稳定命中正确 endpoint。

### Phase 3：引入账号级调度

目标：

- 解决“正式环境账号多，但同模型稳定账号少”的核心问题。

改造内容：

- 为账号增加成功率、延迟、限流、认证状态、并发占用等运行时快照。
- 建立账号级并发上限和账号级速率预算。
- 引入可打破的粘性会话。
- 将账号层排序放在跨站点和全局重试之前。

当前实现：

- 已在 `tokenRouter` 增加账号级运行时状态，记录 `successEma / latencyEmaMs / consecutiveFailures / inflightCount`。
- 已接入账号级并发预算：
  - 默认单账号并发预算 1。
  - 显式 token 通道在稳定且低延迟时可放宽到 2。
- 已接入账号级速率预算：
  - 使用轻量漏桶，按账号成功率、延迟和连续失败动态调整 `capacity / refillPerSec`。
  - `preview` 路径只读预算，不会误消费令牌；真实选中时才扣减。
  - 对明确 `auth / rate_limit` 失败会拉长账号避让窗口；协议错误不会误触发账号长时间降速。
- 已接入请求级粘性会话：
  - HTTP 代理基于 `downstream client context` 生成 `stickySessionKey`。
  - Responses WebSocket 基于 `session-id` 生成会话粘性键。
- 已实现“粘性优先，但账号近期失败或繁忙时自动打破粘性”。
- 已实现账号运行时状态持久化与轻量跨实例共享：
  - 通过 `settings` 分别持久化账号健康、预算与粘性绑定。
  - 粘性键只存 hash，不落原始 session key。
  - 重启或新实例加载后，可恢复账号预算、粘性绑定和 in-flight 近似快照。
- `explainSelection` 与 `/api/routes/diagnostics` 已输出账号级调度快照，支持直接排查账号繁忙、粘性命中和 EMA 状态。

完成定义：

- 同模型请求优先命中最近稳定成功的账号。
- 当某个账号近期连续失败时，系统能自动降低其承压而不是继续重复请求。

### Phase 4：探测治理与安全回退

目标：

- 让协议探测“能用、可控、不伤号”。

改造内容：

- 为 `/api/sites/:id/protocol-probe` 增加站点级冷却和最近成功缓存。
- 将 probe 成功结果保存为“已验证首选 + 安全 fallback 池”，而不是单纯锁死 manual 单路径。
- 探测失败对外返回 attempts 摘要，而不是只吐最后一条错误。
- 所有探测继续坚持单模型有限验证。

完成定义：

- 同一站点短时间重复探测不会持续真实打上游。
- 探测结果既能避错，也保留受控回退能力。

### Phase 5：重构签到状态机与自动恢复

目标：

- 把签到从“日志型任务”升级为“可调度、可恢复、可运营”的状态机。

改造内容：

- 将签到结果枚举收敛成结构化状态机。
- 新增签到快照持久化。
- 自动重登优先基于结构化错误码触发，而不是仅依赖文本。
- 建立站点级签到失败预算、退避和熔断。
- 将 `manual_required`、`unsupported` 变成明确运营态。

完成定义：

- 重启后签到调度上下文不丢。
- 人工可以明确知道哪些账号该等、该重登、该手动处理、该永久跳过。

### Phase 6：诊断与运营工具闭环

目标：

- 让“看得到问题”升级成“能安全处理问题”。

改造内容：

- 在诊断面板显示 endpoint block TTL、preferred 更新时间、站点 breaker 剩余时间、账号级失败预算。
- 增加定向复验、清理 endpoint 记忆、清理熔断、清理站点健康状态的受控入口。
- 让签到待办聚合成明确清单，而不是只看日志。

完成定义：

- 常见线上问题能通过诊断面板定位和恢复，无需翻数据库或临时打日志。

### Phase 7：模型广场与前端闭环体验

目标：

- 保证前端运维入口稳定、一致、可操作。

改造内容：

- 对齐模型广场卡片、表格、移动端详情的检测、诊断、复制能力。
- 检测成功且自动补 Key 时，提供直接复制成功 Key 的动作。
- 异常详情改为抽屉、展开区或侧栏，不再直接撑坏核心表格。
- 在关键结果处增加“复制诊断摘要”“跳转目标记录”等闭环动作。

完成定义：

- 用户无论处于哪个视图，都能完成“检测 -> 诊断 -> 复制 / 跳转”的完整路径。
- 异常详情不会破坏余额等核心列的可读性。

## 优先级建议

### P0：必须优先完成

- 强阻断 + 半开恢复。
- `suggested endpoint` 学习闭环。
- 账号级调度与账号级失败衰减。
- 协议探测冷却与缓存。
- 签到状态机与签到快照。

### P1：显著提升体验

- 站点级失败预算与恢复探测。
- 多模态/文件能力分桶记忆。
- 诊断面板增加可控操作入口。
- 签到人工待办聚合。

### P2：长期运维优化

- 更精细的 `site type profile` 画像。
- 更完整的账号级容量评估和站点容量阈值。
- 模型广场运维体验打磨。

## 验证与上线原则

- 协议探测相关改造必须验证“不会扫全站全部模型”。
- 网关改造必须验证“不会在全部候选失败时立刻撞回刚失败 endpoint”。
- 账号级调度必须验证“同模型少量稳定账号会被优先复用”。
- 签到改造必须验证“manual_required / unsupported / already_checked” 不再污染真正成功口径。
- 所有新记忆层都必须验证“存在 TTL、成功回写、定向复验或手动清理中的至少一种恢复路径”。
